# アーキテクチャレビュー: Salesforce-Notion 同期

## 目的
このドキュメントでは、Salesforce-Notion 同期実装におけるアーキテクチャ上の判断と、その根拠について説明します。大量データの取り扱いやバッチ処理については、[LARGE_DATA_SYNC.md](LARGE_DATA_SYNC.md) を参照してください。

## 現行アプローチの課題

### 1. トランザクションの制約
- フローからトリガされる Apex は、DML 操作と同じトランザクション内で実行されます
- トランザクション内で外部 API コール（Notion API）を行うと、以下の問題が発生します:
  - コールアウトの 10 秒タイムアウト制限
  - トランザクションあたり最大 100 件のコールアウト制限
  - トランザクションロックの問題
  - ユーザー体験の悪化（UI のフリーズ）

### 2. ガバナ制限のリスク
- リレーションシップ処理に伴う複数の API コール
- 大量データ処理時のヒープサイズ制限
- 複雑なリレーションシップ処理時の CPU 時間制限

### 3. エラーハンドリングの難しさ
- API 失敗時にトランザクション全体がロールバックされる
- 部分的な失敗への対応が困難
- レジリエンスのため複雑なリトライロジックが必要

## 推奨アーキテクチャ: フロー駆動の非同期処理

### Invocable Apex + Queueable/Future パターン

```
[Record Change] → [Flow] → [Invocable Apex] → [Queueable/Future] → [Notion API]
```

### メリット:
1. **ユーザーコンテキストの保持**
   - 実行ユーザーの権限を維持
   - 権限セット割り当てを通じて指定ログイン情報と連携
   - 特別な UI 設定は不要

2. **疎結合なアーキテクチャ**
   - UI 操作は即座に完了
   - API コールはバックグラウンドで処理
   - トランザクションをブロックしない

3. **スケーラビリティの基盤**
   - リアルタイム操作を効率的に処理
   - バッチ処理への拡張が容易（LARGE_DATA_SYNC.md を参照）
   - 同期パターンの明確な分離

4. **エラーの分離**
   - API 失敗が DML トランザクションに影響しない
   - エラーは分析のため個別に記録
   - 明確な実行パス

5. **ガバナ制限への準拠**
   - 個別のトランザクションコンテキスト
   - 非同期処理ではコールアウト時間に制限なし
   - リソースの効率的な活用

### コア実装パターン:

ベースとなるアーキテクチャは、リアルタイムかつイベント駆動の同期に最適化されたシンプルなパターンを採用しています:

1. **フロートリガ**: レコード変更を捕捉
2. **Invocable Apex**: 操作種別と件数に応じてルーティング
3. **非同期処理**: 単一レコードは @future、小規模バッチは Queueable
4. **エラーログ**: DML とコールアウトの競合を避けるため非同期でログ記録

リトライ機構、バッチ処理、大量データ処理を含む詳細な実装については、[LARGE_DATA_SYNC.md](LARGE_DATA_SYNC.md) を参照してください。

### 検討した代替アプローチ:

1. **プラットフォームイベント**
   - 長所: 完全に疎結合でスケーラブル
   - 短所: ユーザーコンテキストを失う（自動プロセスユーザーとして実行される）、複雑な認証情報設定が必要

2. **変更データキャプチャ (CDC)**
   - 長所: Salesforce ネイティブ機能、変更の自動追跡
   - 短所: 制御が制限される、追加設定が必要

3. **@future メソッドの直接利用**
   - 長所: シンプルな実装
   - 短所: チェーン不可、エラーハンドリングが限定的、50 コール制限

4. **Batch Apex**
   - 長所: 大量データに適する
   - 短所: リアルタイムではない、最小 1 分の遅延

## 推奨

実装済みの Invocable Apex + 非同期処理パターンは、リアルタイム同期に最適なバランスを提供します:

### 強み:
- ユーザーコンテキストの保持（指定ログイン情報にとって重要）
- リアルタイム処理能力
- クリーンなエラー分離
- 優れたユーザー体験
- シンプルなデプロイモデル

### 特長:
- 実行時のガバナ制限チェックによって任意の件数に対応
- 大量データセットに対する Queueable の自動チェーン
- インテリジェントなチェーンによる全レコードの完全処理
- 手動でのバッチサイズ設定が不要
